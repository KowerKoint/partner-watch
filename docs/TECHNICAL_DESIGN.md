# Partner Watch 技術設計

更新日: 2026-08-30

この文書は、`SPEC.md` を実装可能な設計へ落とし込むための技術選定と、今後決める事項を記録する。

## 1. 前提

- 利用者は交際中の2人のみとする。
- 両者が機能を理解し、互いの端末へ本人の操作でインストール・権限設定する。
- Google Playでは公開せず、署名済みAPKを直接インストールする。
- 対象OSはAndroid 16（API 36）以上とする。
- サーバーは利用者の自宅PCで稼働させる。
- 画面撮影は対象端末の「撮影受付」スイッチが有効な場合だけ実行する。
- OSやアプリが保護している画面は撮影対象外とする。

## 2. システム構成

```text
Android A ── HTTPS / WebSocket ──┐
                                ├── Caddy ── Partner Watch Server ── SQLite
Android B ── HTTPS / WebSocket ──┘                         └── 画像（一時保存）
    ▲                                                        │
    └──────────────── FCMによる再接続通知 ────────────────────┘
```

通常時はWebSocketでオンライン状態と要求を低遅延に配信する。接続が切れている場合はFirebase Cloud Messaging（FCM）を「アプリを起こしてサーバーへ再接続させる通知」として使う。スクリーンショット本体をFCMに載せない。FCMへの依存は許容する。

## 3. 技術選定

### Androidアプリ

| 項目 | 選定 | 状態 | 理由 |
|---|---|---|---|
| 言語 | Kotlin | 確定 | Android標準で、OS APIを直接扱いやすい |
| UI | Jetpack Compose + Material 3 | 確定 | 小規模な設定・状態画面を少ないコードで構築できる |
| 最小SDK | API 36（Android 16） | 確定 | 利用予定端末に合わせ、旧OS互換コードを持たない |
| コンパイルSDK | API 37 | 確定 | 現行AndroidX安定版の要件を満たす。対象OS下限とtarget SDKはAPI 36のまま維持する |
| 画面撮影 | `AccessibilityService.takeScreenshot()` | 仮決定 | 対象端末で毎回MediaProjection確認を出さずに撮影できる |
| バックグラウンド処理 | Foreground Service + FCM + WorkManager | 確定 | 常時接続、切断復帰、遅延処理で役割を分ける |
| HTTP通信 | OkHttp | 仮決定 | HTTPとWebSocketを同じクライアントで扱える |
| ローカル設定 | DataStore | 仮決定 | 小規模な設定値と状態の保存に適する |
| 秘密情報 | Android Keystore | 確定 | 認証鍵や暗号鍵を通常ファイルとして保存しない |

Accessibility Serviceは、初回セットアップ時に各利用者が明示的に有効化する。APKを直接インストールするため、端末設定の「制限付き設定を許可」も必要になる。

Foreground Serviceは実行中であることを示す常時通知を表示する。OSに隠れて監視する動作は設計しない。

### サーバー

| 項目 | 選定 | 状態 | 理由 |
|---|---|---|---|
| 言語 | Go | 確定 | 小さな単一バイナリにでき、自宅PCで運用しやすい |
| API | JSON over HTTPS | 仮決定 | 端末との通信内容が単純で、調査もしやすい |
| リアルタイム通信 | WebSocket | 仮決定 | 撮影要求と状態変化を低遅延に配信できる |
| DB | SQLite（modernc.org/sqlite） | 確定 | 利用者2人では外部DBサーバーが不要で、CGOなしの静的コンテナを維持できる |
| TLS・入口 | 既存のCaddy | 確定 | 所有済み固定ドメインで身内用サービスをすでに運用している |
| 配布 | Docker Compose | 確定 | 既存Caddyとは独立したコンテナとして簡単に起動・更新できる |

サーバーは所有済みの固定ドメインを使ってインターネットへ公開する。Androidアプリにはドメインをハードコードせず、初回セットアップ時に利用者がHTTPSのベースURLを入力する。入力値はAndroid Keystoreで保護した設定と関連付けて保存する。

### サーバー登録の制限

公開サーバーを第三者に利用されないよう、通常のアカウント新規登録APIは設けない。管理者がサーバー上で生成する、十分に長いランダム値を持つ一回限りの招待トークンがある場合だけ端末登録を許可する。

- 招待トークンは256ビット以上の暗号学的乱数とする。
- トークンには短い有効期限を設け、一度使用したら即時無効化する。
- ペア作成時に、同じペアへ所属するslot 1とslot 2用の招待トークンを1つずつ発行する。各トークンは対応する1台にしか使用できない。
- 招待トークンと端末認証トークンは平文でDBへ保存せず、SHA-256ハッシュだけを保存する。
- URLのクエリ文字列はCaddyやアプリのログへ残る可能性があるため、秘密値をクエリ文字列には入れない。
- 招待QRコードはサーバーURLとトークンを含むアプリ用データとし、ブラウザーでアクセスするURLとしては扱わない。アプリは読み取ったトークンをHTTPSのPOST本文で送る。
- 手入力に対応する場合も、サーバーURLと招待コードを別の入力欄にし、秘密値をURLへ連結しない。
- 登録入口を含む非公開APIは、形式不正、無効トークン、期限切れの場合に詳細を明かさず`404 Not Found`を返す。
- 登録後の通常APIは、URLの複雑さではなく端末固有の認証情報で保護する。
- Caddyとアプリケーションのログにはトークン、認証情報、画像を記録しない。

## 4. 撮影フロー

1. AがBの「スクリーンショット撮影」を押す。
2. サーバーはAがBとペアであること、要求頻度、要求IDを検証する。
3. BがWebSocket接続中なら要求を即時配信する。未接続ならFCMで再接続を促す。
4. Bはローカルの撮影受付スイッチを確認する。
5. 無効、Accessibility Service停止、画面ロック、保護画面などの場合は、理由を分類して結果を返す。
6. 撮影可能ならAccessibility Serviceで撮影し、圧縮してHTTPSでアップロードする。
7. Aが画像を取得したら、サーバー上の一時データを即時削除する。未取得でも作成から1時間で削除する。
8. Aは取得した画像を端末へ明示的に保存できる。自動では端末の共有ストレージへ保存しない。

要求には一意なIDと短い有効期限を設定し、再送による重複撮影を防止する。

### 画像仕様

- 形式はJPEGとする。
- エンコード品質の初期値は85とする。
- 1画像のアップロード上限は10 MiBとする。
- デコード後の画素数にも上限を設け、初期値は500万画素とする。
- EXIFなどのメタデータはアップロード前に付与せず、サーバーでも引き継がない。
- サーバーは拡張子や`Content-Type`だけでなく、JPEGの実体と画像寸法を検証する。

Pixel 8aは1080×2400、Galaxy A25 5Gは1080×2340で、約253万～259万画素となる。非圧縮RGBAでは約9.7～9.9 MiBだが、品質85のJPEGでは画面内容により数百KiB～数MiB程度が想定される。ノイズや写真が全面に表示された圧縮しにくい画面にも余裕を持たせ、異常に大きいアップロードは拒否できる値として10 MiBを採用する。

## 5. 状態の定義

単純な「オンライン／オフライン」だけでなく、少なくとも以下を区別する。

- `AVAILABLE`: 接続中、撮影受付中、Accessibility Service有効
- `DISABLED`: 本人が撮影受付スイッチを無効化
- `SERVICE_UNAVAILABLE`: Accessibility Serviceが無効または停止
- `LOCKED`: 端末状態により撮影不可
- `OFFLINE`: 一定時間サーバーへの通信なし
- `CAPTURE_PROTECTED`: 対象画面がOSまたはアプリによって保護されている
- `TIMEOUT`: 要求の有効期限内に結果なし

「電源オフ」と「通信圏外」と「アプリ強制停止」は、サーバーからは厳密に判別できないため、まとめて`OFFLINE`として扱う。

## 6. セキュリティとプライバシー

- 初回ペアリングは、片方が表示した短時間有効なQRコードをもう片方が読み取る方式とする。
- ペアリング後は端末ごとに個別の認証鍵を持たせる。
- 通信はすべてTLS 1.3を使用する。
- スクリーンショットをログやバックアップへ含めない。
- サーバー上の画像は最大1時間だけ保存し、取得成功後は即時削除する。
- 画像を取得した利用者が端末へ明示的に保存することは許可する。
- 端末へ保存する場合はAndroidのMediaStoreを使用し、写真コレクションへJPEGとして追加する。
- 撮影要求、成功・失敗、設定変更は監査履歴として双方から確認できるようにする。
- 撮影受付スイッチの変更は相手へ通知し、サーバー履歴にも残す。
- レート制限を設け、連続撮影や誤操作を防ぐ。
- アプリは永続通知を表示し、サービス稼働を端末所有者から隠さない。

初期版ではスクリーンショットのエンドツーエンド暗号化を行わず、HTTPSで通信経路を暗号化する。HTTPSは端末とサーバー間の盗聴・改ざんを防ぐが、サーバープロセスは受信画像を復号できる。このリスクは、サーバーを利用者自身が管理すること、保存を最大1時間に制限すること、取得後に即時削除することで受容する。サーバーでは画像ファイルのアクセス権を専用サービスユーザーに限定し、バックアップ対象から除外する。

## 7. 再起動と障害時の動作

- ログイン情報、ペア情報、撮影受付設定は再起動後も保持する。
- `BOOT_COMPLETED`後に、OSが許す範囲で通常の通信サービスを復帰させる。
- Accessibility Serviceの有効状態を確認し、無効なら本人へ通知する。
- 常時接続が切れた場合は指数バックオフで再接続する。
- FCMは配信保証ではないため、FCMだけをオンライン判定に利用しない。
- サーバー停止中の撮影要求は受理済みにせず、要求元へ到達不能として表示する。
- サーバーへ一定時間接続できない場合はAndroidアプリ自身がローカル通知を出す。停止中のサーバーからFCMを送ることはできないため、サーバーダウン通知をFCMだけには依存させない。

## 8. 制限値と保持期間

- 同一端末からの撮影要求は10秒に1回までとする。
- 同一端末からの撮影要求は、上記に加えて直近1時間で60回までとする。
- 撮影要求は発行から1分でタイムアウトとする。
- 成否にかかわらず、受理した撮影要求を回数制限へ算入する。
- 監査履歴は作成から1か月で削除する。
- 監査履歴には画像本体、招待トークン、認証情報を含めない。
- 上限判定はサーバー側で行い、端末時刻には依存しない。

## 9. 将来機能

位置情報はAndroidのバックグラウンド位置情報権限が必要になるため、スクリーンショット機能とは別に本人が有効化する。バッテリー残量と充電状態は定期送信ではなく、状態変化または適度な間隔で送信する。

位置履歴は初期版では保存せず、現在位置のみ共有する案を推奨する。

## 10. 未決事項

以下は実装開始前または該当機能の着手前に決定する。

1. Pixel 8aとGalaxy A25 5Gそれぞれで必要な省電力除外設定。事前決定ではなく実機検証で確定する。
2. JPEG品質85での実際のファイルサイズと視認性。実機検証結果により変更できる。
3. Dockerイメージをローカルビルドするか、プライベートレジストリへ置くか。
4. 2026年9月以降のAndroid開発者確認制度について、個人配布APKの登録・署名手順を実機導入前に確認する。

## 11. 初期リリース範囲

最初の動作確認版には以下だけを含める。

- 2台のペアリング
- 撮影受付スイッチと相手への状態反映
- WebSocket/FCMによる撮影要求
- Accessibility Serviceによるスクリーンショット
- 画像の受け渡しと自動削除
- オンライン、拒否、サービス停止、タイムアウトの表示
- 最低限の要求履歴

位置情報とバッテリー共有は、撮影フローの安定性を確認した後に追加する。
