# 通知転送 仕様

更新日: 2026-09-11

## 1. 初期仕様

- Android端末へ表示された通知を、ペア相手の端末へPartner Watchの通知として転送する。
- Androidは通知がFCMなどのプッシュ配信由来か、アプリ内で生成されたものかを確実に区別できないため、初期版は端末へ表示された通知を対象とする。
- 転送は端末ごとの設定とし、既定値は無効にする。
- 有効化にはAndroidの「通知へのアクセス」を端末所有者が明示的に許可する必要がある。
- 受信側ではアプリごとに通知を偽装せず、すべてPartner Watchの単一通知チャンネルから表示する。
- 受信通知チャンネルは既定でサイレント（音・バイブレーションなし）とする。利用者はAndroid設定で変更できる。
- Partner Watch自身の通知、常駐通知、グループ要約、タイトルと本文がともに空の通知は転送しない。
- 初期版ではアプリ名、パッケージ名、タイトル、本文、元の通知時刻を転送する。アイコン、画像、操作ボタン、PendingIntentは転送しない。
- 通知の更新も新しいイベントとして扱うが、短時間に同一内容が再通知された場合は端末側で抑制する。

## 2. 配送と保存

1. 送信端末の`NotificationListenerService`が通知を取得する。
2. 端末の転送設定と除外条件を確認し、認証済みHTTPSでサーバーへ送る。
3. サーバーは相手側に属する各端末の配送行を作成する。
4. 接続中の端末にはWebSocket、未接続端末にはFCMで新着だけを通知する。
5. 受信端末は認証済みHTTPSで本文を取得してPartner Watchのサイレント通知を表示し、受領をサーバーへ報告する。

FCMデータには通知タイトルや本文を載せず、取得を促すイベント種別だけを載せる。通知本文と未受領の配送行は作成から1時間で削除する。アプリケーションログと監査履歴へタイトル・本文・パッケージ名を記録しない。

## 3. 制限

- アプリ名は120文字、パッケージ名は255文字、タイトルは500文字、本文は4,000文字までとする。
- 1送信端末につき10秒間に20件、1時間に500件までとする。
- サーバーが受理したことは配送完了を意味しない。FCM停止、受信端末の通知拒否、オフラインが1時間を超えた場合は表示されない。
- HTTPSで経路は暗号化するが、初期版ではE2EEを行わないためサーバー管理者は保存中の本文を読める。このリスクは自宅運用と1時間保持で受容する。

## 4. 複数端末・他OSへの拡張

現在の`slot 1`と`slot 2`は「端末」ではなく、将来はペア内の「利用者側」を表す識別子として扱う。通知イベント本体と端末ごとの配送状態を分離し、送信元と反対側に登録された全端末へ配送できる構造にする。

- Android: FCMとWebSocketを利用する。
- Linux/Windows: WebSocketまたは定期取得を利用する。
- iPad: APNsを利用する。
- 各端末は個別の認証鍵、表示名、プッシュトークン、失効状態を持つ。
- 将来の登録変更では`devices(pair_id, slot)`の一意制約を外し、同じslotへ複数端末を登録できるようにする。
- ある端末で通知を受領しても、同じ利用者側の別端末の配送状態は独立させる。

複数端末の登録UI、端末失効、Android以外のクライアントは今回の実装範囲に含めない。

## 5. 受信フィルター

受信側の利用者は、相手側から転送される不要な通知を拒否するルールを管理できるようにする。ルールは個々の受信端末ではなくペア内の利用者側（slot）に属し、将来同じ利用者が複数端末を登録した場合にも共通で適用する。

### 5.1 ルール

1つのルールには次の条件を任意に指定できる。

- 送信元端末: 安定した端末IDとの完全一致。UIには端末名も表示する。
- 送信元アプリ: Androidではパッケージ名、Linuxではdesktop entryなど送信元が報告した識別子との完全一致。UIにはアプリ名も表示する。
- 通知タイトル: タイトルとの「含む」または「完全一致」。LINEなど、タイトルに送信者名を表示するアプリでは「アプリ=LINE、タイトルに相手の名前を含む」として二人の会話を除外できる。ただしアプリによる表示形式の変更には影響される。
- メッセージ: タイトルと本文を改行で連結した文字列との「含む」または「完全一致」。大文字・小文字を区別せず、Unicodeを正規化して比較する。

同じルール内で入力された条件はすべて満たした場合に拒否し、複数ルールのいずれかに一致すれば拒否する（条件間はAND、ルール間はOR）。条件が1つもないルールは保存できない。表示名は識別を助ける情報として保存してよいが、一致判定には安定したIDを使う。

### 5.2 判定場所と配送

初期実装では、認証済みの送信端末から通知を受け取ったサーバーが、相手側slotのルールを判定する。一致した通知は通知本体も端末別配送行も作成せず、WebSocketイベントおよびFCMも送信しない。受信Androidでも保存済みルールを再確認し、設定更新との競合や古いサーバーとの組み合わせで拒否対象を表示しないようにする。

この方式では送信端末からサーバーまでのHTTPS要求は発生する。一方、受信者の拒否ルール、とくにメッセージ文字列を相手側の端末へ開示せず、ルール変更を即座に全受信端末へ反映できる。送信前に通信を完全に止める方式は、拒否ルールを送信側へ配布する必要があるため初期実装には含めない。

### 5.3 Android UI

- 端末設定の「受信する通知」から、拒否ルールの一覧、追加、編集、有効・無効化、削除を行える。
- 編集画面は「送信元端末」「アプリ」「通知タイトル」「タイトル・本文」の入力欄、各文字列条件の「含む／完全一致」選択、自然文の条件プレビューを表示する。
- 転送通知に「この種類の通知を受信しない」アクションを表示する。
- 通知アクションは即座に拒否登録せず、送信元端末とアプリが入力済みの編集画面を開く。利用者は条件を外したり、メッセージ文字列を追加したりしてから保存する。
- 元通知のタイトルを「送信者名などとしてタイトル条件に使う」候補として提示するが、自動では条件に含めない。タイトル・本文全体をメッセージ条件へ自動入力せず、変動する時刻や件数まで含めた効かないルールができることを避ける。
- 通知アクションから画面を開くために必要な送信元情報は、Android通知のIntentへ保持する。サーバー上の通知が受領済みになった後も編集画面を開けるようにする。

フィルターは転送機能全体の有効・無効とは独立させる。ルール作成時には、たとえば「thinkpad-nixosのDiscordを拒否」のように実際の効果を確認できる文を表示し、広すぎる設定を誤って保存しにくくする。

送信側には、通知転送という主目的を送信者が任意に弱められる除外UIを設けない。大量送信への対策は、Partner Watch自身、常駐通知、グループ要約、空通知の機械的除外、短時間の同一内容重複抑制、端末単位のレート制限で行う。これらは通知内容の選別を送信者へ委ねず、暴走時のバッテリー・通信量・サーバー負荷を制限するための安全策として扱う。
